## 1. Зачем

Сейчас модель заклинаний — **монокастер**:

| Что в коде | Поведение |
|------------|-----------|
| `SpellsState.casting_ability` | **одна** характеристика |
| Desk / панель | **один** блок «Сл. спас. / Атака» |
| `resolveSpellLearnBudget` | mode + cantrips + known от **первого** кастера |
| `suggestSpellcastingFromClasses` | `casting_ability` = ability **первого** класса с casting |

Это ломает любой мультикласс с **разными** хар-ками и разными режимами обучения:

- Изобретатель (ИНТ, prepared) + Колдун (ХАР, known + pact)
- **Бард (ХАР, known) + Волшебник (ИНТ, spellbook) + Колдун (ХАР, known + pact)** ← целевой стресс-кейс

Правило PHB: заклинание принадлежит классу → атака и Сл считаются по **характеристике этого класса**. Ячейка (shared / pact) характеристику не меняет.

## 2. Правила (канон для продукта)

### 2.1. Три независимых оси

| Ось | Что объединяется | Что остаётся раздельным |
|-----|------------------|-------------------------|
| **Ячейки** | Shared slots по таблице MC; pact — отдельно | — |
| **Пулы знания/подготовки** | — | По классу: known / prepared_list / spellbook |
| **Характеристика каста** | — | По классу-источнику заклинания |

### 2.2. Пример: Бард 6 / Волшебник 8 / Колдун 6 (уровень 20)

| Класс | Режим | Хар-ка | Бюджет (пример) | Атака / Сл (БМ +6) |
|-------|-------|--------|-----------------|-------------------|
| Бард 6 | known | ХАР | заговоры + known по таблице барда 6 | по ХАР |
| Волшебник 8 | spellbook | ИНТ | книга + prepare по wizard 8 | по ИНТ |
| Колдун 6 | known + pact | ХАР | заговоры + known по warlock 6; ячейки договора отдельно | по ХАР |

Shared slots: MC caster level = bard 6 + wizard 8 (+ warlock **не** в shared) → слоты по таблице full caster 14.  
Pact: отдельные ячейки колдуна 6.

**Два профиля ХАР не сливаются в один «слот UI»:** бард и колдун оба на ХАР → **один** блок «ХАР: Сл / Атака», но **два** бюджета знания и два списка.

### 2.3. Что считать «источником» заклинания

| Строка на листе | `cast_ability` |
|-----------------|----------------|
| Из списка / known / книги класса X | ability класса X |
| Always-prepared домен/клятва/подкласс | ability того же класса |
| Pact of the Tome cantrips | **ХАР** (это feature колдуна; заговоры «из любого списка», но каст — warlock) |
| Раса / черта с явной ability в гранте | из гранта |
| Homebrew без метки | fallback: выбранный игроком профиль **или** primary caster |

## 3. Целевая модель данных

### 3.1. Профили каста (новое)

```ts
type SpellCastProfile = {
  /** Стабильный ключ: classEntryId или 'warlock' / 'wizard' / … */
  id: string
  slug: string          // artificer | bard | wizard | warlock | …
  labelRu: string
  ability: SpellcastingAbility
  mode: SpellLearnMode  // known | prepared_list | spellbook
  /** alone-max уровень для membership списка класса */
  aloneMaxLevel: number
  cantripsBudget: number
  leveledKnownBudget: number | null
  maxPrepared: number | null
}
```

На листе / в sync: `spells.cast_profiles: SpellCastProfile[]` (деривится из `classes[]` + abilities + PB; можно не персистить целиком, а кэшировать computed).

**Deprecated:** одиночный `casting_ability` как единственный источник правды.  
Миграция: оставить поле как **primary/default** для старых листов и UI без профиля; при чтении — если есть classes → пересчитать profiles.

### 3.2. Метка на заклинании

На `SheetSpell` добавить:

```ts
/** Класс-владелец для DC/атаки и бюджета. null = innate/feat/custom. */
class_slug?: string | null
class_entry_id?: string | null
```

Заполняется при: create pick, grimoire learn/prepare, grant sync (tome → warlock), subclass always-prepared.

### 3.3. Бюджеты — сумма по классам, не «первый класс»

`resolveSpellLearnBudget` → **`resolveSpellLearnBudgets`** (массив):

- cantrips: **сумма** таблиц по каждому кастеру (изобретатель 15 = 4 + колдун 5 = 3 → **7**, плюс tome +3 вне бюджета);
- leveled known: **по профилю**, не один общий счётчик;
- prepare: **по профилю** (изобретатель и жрец не делят один max_prepared);
- mode для UI: если профилей > 1 → режим **`multiclass`** (см. §4), не «режим первого».

Баг Квакка («4/4 изобретателя блокирует колдуна») закрывается этим срезом.

### 3.4. Резолв атаки / Сл при касте

```ts
function resolveCastStats(spell, profiles, abilities, pb, modifiers):
  ability = spell.class_slug
    → profiles.find(slug)?.ability
    → grant.ability
    → profiles[0]?.ability   // last resort
  return { dc, attack } from ability + pb + modifiers
```

Cast dialog / combat log / classic sheet card — все через одну функцию.

## 4. UX / UI-кит (играбельность)

Принцип: **в бою игрок смотрит на заклинание, а не выбирает характеристику вручную.** Профили — справочная шапка; на строке заклинания уже видны нужные цифры.

### 4.1. Шапка каста (Desk + SpellsPanel)

**Сейчас:** один блок `Сл. спас. · Атака`.

**Цель:**

| Число уникальных abilities среди профилей | UI |
|-------------------------------------------|----|
| 0 | скрыть |
| 1 | как сейчас (одна пара), подпись хар-ки мелким |
| 2+ | ряд мини-профилей: чип `ИНТ` / `ХАР` / `МДР` с парой Сл·Атака |

Цвета чипов = уже существующие ability tokens UI-кита (`int` Чернила, `cha` Слива, `wis` Листва…).  
Доска: обновить `dvarf-ui-kit-spells.jpg` (+ при необходимости desk).

**Не делать:** табы «переключить активную характеристику» как обязательный жест перед кастом — это ломает бой.

### 4.2. Строка заклинания

На compact / полном списке:

- маленький badge класса (`Бард` / `Визад` / `Колд`) **или** цветной ability pip;
- при hover/detail: `Сл 18 · +10 (ХАР)`.

В CastSpellDialog шапка всегда показывает **уже посчитанные** Сл/атаку для *этого* заклинания (не глобальные).

### 4.3. Гримуар (связь с SPELL_ACCESS_UX)

Мультикласс = **секции или фильтр по профилю**, не один mode на весь экран:

| Фильтр / секция | Режим кнопок |
|-----------------|--------------|
| Бард | Выучить / Забыть |
| Волшебник | В книгу → Подготовить |
| Колдун | Выучить / Забыть |
| Все | смешанный список с badge |

Лимиты и alone-max — **внутри секции**.  
«Все доступные» prepared_list не смешивается с known-бюджетом барда.

План гримуара (§7 SPELL_ACCESS) дополняется: **не один `spellAccessUiCopy(mode)`, а copy от активного профиля / секции.**

### 4.4. Create / Level-up

Отдельные шаги (или аккордеон) **на каждый кастер-класс**:

1. Заговоры класса A (бюджет A, список A)  
2. Known / prepare / book класса A  
3. … то же для B, C  
4. Pact tome (если есть) — **вне** бюджетов A/B  

Блокер «Далее»: невыполненный бюджет **текущего** профиля, а не суммарный 4/4 чужого класса.

Квакк: после фикса мастер даёт выбрать cantrips+known колдуна независимо от изобретателя.

### 4.5. Классический лист (P3)

Вместо одного «Класс заклинателя / хар-ка / Сл / атака»:

- таблица профилей (2–3 строки), или  
- «основной» + ссылка «ещё N» в notes, если печатаем в жёсткий 2014 layout.

Печать: предпочтительно **все** профили компактной строкой под шапкой.

## 10. Критерий «готово» для линии

1. Бард + Волшебник + Колдун: два ability-профиля в шапке; три бюджета; каст считает правильную хар-ку.  
2. Изобретатель + Колдун (Квакк): Сл/атака раздельно; cantrips/known колдуна настраиваются.  
3. Mono-кастер визуально не усложнился (один блок как сейчас).  
4. UI-kit обновлён (tokens ability на spell chrome).  
5. Selfchecks + create smoke на оба кейса.  
6. Нет второго источника правды: только `buildCastProfiles` + `resolveSpellCastStats`.

## 11. Что не делаем в этой линии

- Точечные `if (grung)` / `if (квакк)`.  
- Слияние бард+колдун в один «ХАР known пул» — **неверно по правилам**.
